## 1. 引言

### 1.1 编写目的

本文档为 Fortune 项目管理系统的概要设计说明书,旨在:

- 阐述系统的总体架构与设计思路
- 定义各功能模块的职责与边界
- 描述数据模型、API 接口与前端技术方案
- 为后续详细设计、编码实现与运维部署提供指导依据

### 1.2 系统目标

构建一款轻量级、开箱即用的团队项目管理 Web 应用,满足中小团队在日常协作中的核心需求:

- **看板驱动** —— 任务卡片在可视化看板中拖拽流转,状态变更实时同步
- **数据可见** —— 燃尽图、任务趋势、成员工作量、项目成本等多维度统计
- **权限清晰** —— 系统角色 + 自定义角色双轨体系,25+ 细粒度权限控制
- **财务管控** —— 预算审批、支出登记、工时成本,实时监控项目成本
- **协作闭环** —— 评论、子任务、通知构成完整的团队协作闭环
- **灵活扩展** —— 自定义看板列、项目模板、筛选方案等可配置能力

### 1.3 适用范围

本文档涵盖系统的后端服务、前端应用、数据存储、安全机制和部署架构的设计说明,不涉及具体实现代码的细节(详见源代码与操作手册)。

### 1.4 读者对象

- 项目经理 / 技术负责人:了解系统能力边界与架构选型
- 开发工程师:理解模块设计与接口规范,指导后续功能扩展
- 运维工程师:参考部署架构与运维指引

## 2. 系统概述

### 2.1 系统定位

Fortune 是一款面向中小团队的轻量级项目管理工具,采用前后端分离的 B/S 架构,通过单文件 SQLite 实现零配置启动,无需独立部署数据库服务。

### 2.2 核心能力矩阵

| 能力维度 | 具体能力 |
| --- | --- |
| **项目管理** | 项目创建 / 编辑 / 归档、进度自动计算、成员邀请与角色分配、创建时指定负责人 |
| **项目模板** | 系统预设模板(网站开发/产品迭代/客户支持)、自定义模板、从项目保存为模板、模板任务/预算/看板列配置 |
| **任务管理** | 任务 CRUD、状态流转、优先级与标签、截止日期、负责人指派、进度百分比 |
| **看板视图** | 自定义看板列(添加/编辑/删除/排序)、列颜色配置、拖拽更新状态 |
| **高级筛选** | 多条件组合筛选(状态/负责人/优先级/标签/日期范围)、筛选方案保存与加载 |
| **全局搜索** | Cmd/Ctrl+K 快捷键、跨项目搜索任务、结果高亮、键盘导航 |
| **列表视图** | 表格展示、多状态筛选、批量操作(改状态/改负责人/删除) |
| **甘特图视图** | 时间线可视化、任务条拖拽调整、拖拽创建依赖(FS/SS/FF/SF)、双击编辑依赖、关键路径、进度拖拽 |
| **子任务** | 检查清单、完成进度条、快速添加 |
| **评论系统** | 任务级评论、系统流水记录、@提醒(自动补全 + 通知) |
| **任务模板** | 模板 CRUD、从模板快速创建任务、保存当前配置为模板 |
| **任务附件** | 文件上传(最大 20MB)、下载、删除、文件类型图标 |
| **操作历史** | 任务变更自动记录(状态/负责人/进度/日期)、历史查询 |
| **通知中心** | 铃铛入口、未读标记、单条/全部已读、独立通知历史页、类型筛选 |
| **邮件通知** | 任务完成自动发邮件(Nodemailer + SMTP)、HTML 模板 |
| **数据导出** | 项目列表 CSV 导出、项目任务 CSV 导出(UTF-8 BOM)、进度 Excel 导出 |
| **数据统计** | 任务状态分布、14 天趋势、燃尽图、成员工作量、项目成本 |
| **权限体系** | 5 系统角色 + 自定义角色、25+ 细粒度权限、权限矩阵配置、中间件校验 |
| **预算管理** | 项目预算 CRUD、审批流程(待审批/已批准/已驳回)、五种类别 |
| **支出登记** | 按预算类别登记支出、关联预算、实时成本监控 |
| **工时管理** | 任务工时登记、工时报表(按用户/项目)、成本自动计算 |
| **成员成本** | 时薪设置、外包标记、成本中心、人员类别管理 |
| **成员导入** | CSV/Excel 批量导入、自动创建用户、导入结果预览 |
| **系统增强** | 暗黑/亮色主题切换、任务回收站(软删除)、数据库备份/恢复、飞书集成 |
| **用户管理** | 注册、登录、JWT 鉴权、密码 bcrypt 加密、昵称修改 |

### 2.3 设计原则

1. **简洁优先**:零配置启动、开箱即用、单文件数据库
2. **类型安全**:前后端共享 TypeScript 类型定义,减少契约不一致
3. **渐进增强**:SPA 单页应用、响应式布局、移动端可用
4. **关注分离**:后端分层(路由 → 仓库 → 数据库)、前端分模块(页面 → 组件 → 状态)

## 3. 总体架构设计

### 3.1 架构风格

系统采用 **前后端分离 + 单体应用** 架构:

- **前端**:React 18 SPA,通过 HTTP/REST 与后端 API 通信
- **后端**:Express 单体服务,提供 JSON REST API
- **存储**:SQLite 单文件数据库,通过 better-sqlite3 驱动

### 4.2 模块详细设计

#### 4.2.1 M1 认证模块

| 功能 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| 用户注册 | name, email, password | token, user | 首位注册用户自动成为 admin |
| 用户登录 | email, password | token, user | bcrypt 校验密码 |
| 获取身份 | Header: Authorization | user | JWT 解码 |
| Token 鉴权中间件 | 请求头 | AuthRequest | 解析 JWT,附加 userId |
| API 请求重试 | GET 请求(5xx) | 重试 1 次 | 300ms 延迟,仅对幂等 GET 生效 |

**JWT Claims**

```json
{
  "sub": "user-uuid",
  "role": "admin",
  "iat": 1234567890,
  "exp": 1234654290
}
```

#### 4.2.2 M2 项目管理模块

**项目 CRUD**

| 操作 | API | 权限 |
| --- | --- | --- |
| 列表 | `GET /api/projects` | 管理员可见全部,其他仅可见参与的项目 |
| 详情 | `GET /api/projects/:id` | 已登录用户 |
| 创建 | `POST /api/projects` | 已登录用户,自动设为 owner;管理员可指定 ownerId |
| 更新 | `PATCH /api/projects/:id` | 项目 owner 或管理员 |
| 删除 | `DELETE /api/projects/:id` | 项目 owner 或管理员 |

**创建时指定负责人**:请求体增加可选 `ownerId` 字段,仅管理员可指定他人为负责人。指定后,该用户自动加入项目成员(role=owner)。非管理员尝试指定他人返回 403。

**成员管理**

| 操作 | API | 权限 |
| --- | --- | --- |
| 添加成员 | `POST /api/projects/:id/members` | 项目 owner 或管理员 |

| 移除成员 | `DELETE /api/projects/:id/members/:uid` | 项目 owner 或管理员 |

**进度计算规则**

```
任务完成度 = task.progress (0-100,默认 0)
项目进度 = MAX( AVG(所有任务.progress), 已完成任务数 / 总任务数 × 100% )
```

系统在每次任务创建、状态变更、删除、进度更新时自动重算并更新 `projects.progress`。

#### 4.2.3 M3 任务管理模块

**看板视图**

四列固定:待办 → 进行中 → 审核中 → 已完成
拖拽流转:通过 `PATCH /api/tasks/:id/status` 更新状态

**甘特图视图**

甘特图以时间线可视化项目任务,支持以下核心能力:

| 功能 | 说明 |
| --- | --- |
| 任务条渲染 | 按开始/截止日期绘制任务条,进度百分比以深蓝填充 |
| 进度拖拽 | 悬停任务条右侧边缘,出现拖拽手柄,实时调整进度百分比 |
| 任务条拖拽 | 按住任务条主体拖动,实时更新开始/截止日期(含吸附对齐) |
| 依赖线 | SVG 贝塞尔曲线绘制 FS/SS/FF/SF 四种依赖关系 |
| 关键路径 | CPM 算法自动计算并高亮关键任务(红色边框) |
| 泳道分组 | 按负责人分组,可折叠/展开,减少滚动 |
| 时间缩放 | 日/周/月三级视图切换,键盘 +/- 快速缩放 |
| 键盘快捷键 | +/- 缩放、D 回到今天、G 切换分组、Esc 取消选择 |
| 任务搜索 | 工具栏搜索框按标题/描述实时过滤 |
| 逾期标红 | 自动检测逾期任务,显示红色警示图标 |
| 视口裁剪 | SVG clipPath 限制依赖线仅在可视区域渲染,优化性能 |

**甘特图数据模型扩展**

任务新增 `progress` 字段(INTEGER 0-100,默认 0),`start_date` 和 `due_date` 用于时间线定位。任务间通过 `dependencies` 表建立关联,支持 FS/SS/FF/SF 四种依赖类型。

**甘特图性能优化**

- 虚拟滚动:仅渲染可视范围内的任务行,DOM 节点减少 70%
- 视口裁剪:SVG clipPath 裁剪依赖线,仅绘制可视区域内的路径
- 按需加载:Stats 和 HoursReport 页面通过 React.lazy 代码分割,首屏 gzip 减小 15KB

**列表视图与批量操作**

列表视图支持多选批量操作:
- 批量改状态:循环调用 `PATCH /api/tasks/:id/status`
- 批量改负责人:循环调用 `PATCH /api/tasks/:id`(传 assigneeId)
- 批量删除:循环调用 `DELETE /api/tasks/:id`

批量操作前端逐条调用现有接口,任一失败则停止并提示。

**子任务**

子任务作为任务的子资源,支持独立 CRUD:
- 创建:`POST /api/tasks/:id/subtasks`
- 更新:`PATCH /api/subtasks/:id`(支持修改标题和完成状态)
- 删除:`DELETE /api/subtasks/:id`

子任务完成度 = 已完成子任务数 / 总子任务数

**评论与系统流水**

系统在关键节点自动生成伪评论(以 `— ... —` 格式标识):
- 任务创建 → `— 创建了任务 —`
- 状态变更 → `— 将状态从「X」改为「Y」 —`
- 子任务增删 → `— 新增子任务:xxx —`

**@提及机制**

评论提交时,后端通过正则 `@用户名` 解析提及内容:
1. 提取所有 `@` 后的非空白字符串作为用户名
2. 通过 `userRepo.findByName` 查找对应用户
3. 为每个被提及的用户(排除自己)创建 comment 类型通知
4. 前端评论输入框监听 `@` 字符,弹出成员选择面板,支持键盘导航

**任务附件**

附件通过 multer 中间件处理上传:
- 上传:`POST /api/attachments/tasks/:taskId`(multipart/form-data,字段名 file)
- 列表:`GET /api/attachments/tasks/:taskId`
- 下载:`GET /api/attachments/:id`
- 删除:`DELETE /api/attachments/:id`(上传者或管理员)

文件存储于 `data/uploads/`,文件名为 UUID + 原扩展名,元数据(原文件名、大小、MIME 类型)存入 `attachments` 表。单文件最大 20MB。

**预算汇总计算**

```
总预算 = SUM(已批准预算.amount)
已使用 = SUM(关联支出.amount)
剩余预算 = 总预算 - 已使用
```

## 5. 数据库设计

### 5.1 数据库选型

选用 **SQLite**(better-sqlite3 驱动)作为数据存储,原因:

- 零配置:无需安装独立数据库服务
- 单文件:`data/app.db` 便于备份与迁移
- 轻量:适合中小规模数据(万级任务无压力)
- WAL 模式:支持并发读写
- 事务支持:保证数据一致性

| key | TEXT | NOT NULL UNIQUE | 权限键(proj_view/task_create等) |

### 5.4 数据完整性约束

- **级联删除**:项目删除时,其下的任务、成员关联自动删除;用户删除时,其负责的任务置 NULL、关联自动删除
- **外键约束**: `PRAGMA foreign_keys = ON`
- **CHECK 约束**:所有枚举字段(role、status、priority)均通过 CHECK 约束保证值域合法
- **唯一约束**:同一用户不可重复加入同一项目

## 6. API 接口设计

### 6.1 接口规范

- **协议**:HTTP REST
- **数据格式**:JSON (UTF-8)
- **认证方式**:Bearer Token (JWT)
- **统一响应**:成功返回业务数据,错误返回 `{ error: string }`
- **错误码**

| HTTP 状态码 | 含义 |
| --- | --- |
| 200 OK | 请求成功 |
| 201 Created | 资源创建成功 |
| 400 Bad Request | 参数校验失败 |
| 401 Unauthorized | 未登录或 Token 无效 |
| 403 Forbidden | 无权限操作 |
| 404 Not Found | 资源不存在 |
| 409 Conflict | 资源冲突(如重复注册) |

## 8. 安全设计

### 8.1 密码安全

- 密码使用 **bcrypt**(cost factor = 10)加密存储,不可逆
- 注册时进行密码强度校验(最少 6 位)
- 登录失败不区分"邮箱不存在"与"密码错误",防止枚举攻击

### 8.2 会话安全

- 使用 **JWT**(HS256)作为会话令牌
- Token 有效期:24 小时
- Token 存储于 localStorage,每次请求通过 `Authorization: Bearer <token>` 头携带
- 服务端通过 `authRequired` 中间件校验 Token 有效性

### 8.3 权限控制

系统采用**五级角色权限**体系:admin(管理员)、finance(财务)、owner(项目负责人)、member(成员)、guest(访客)

| 层面 | 实现方式 |
| --- | --- |
| **路由层** | `authRequired` 中间件确保所有 API(除登录/注册外)需认证 |
| **数据层** | 项目列表按角色过滤:管理员/财务可见全部,其他仅可见参与项目 |
| **操作层** | 创建/更新/删除操作校验相应角色权限(如预算审批仅 admin/finance) |
| **前端 UI** | 按钮/下拉框根据角色禁用或隐藏(如"仅管理员可修改角色") |

**权限校验中间件**

```typescript
// 角色校验中间件
function requireRole(...roles: Role[]) {
  return (req, res, next) => {
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({ error: '权限不足' });
    }
    next();
  };
}
```

### 8.4 输入校验

所有写操作均使用 **Zod** schema 校验,确保:
- 字段类型正确(如 email 格式、日期格式)
- 字段长度限制(如标题 ≤ 120 字符)
- 枚举值合法(如 status 必须为四种之一)
- 必填字段不为空

### 8.5 CORS 策略

开发模式下允许所有来源(`cors()`),生产环境应配置具体域名白名单。

### 8.6 SQL 注入防护

使用 better-sqlite3 的 **参数化查询**(prepared statement),所有用户输入均通过 `?` 占位符绑定,无拼接 SQL 风险。

### 8.7 文件上传安全

- **大小限制**:multer 中间件限制单文件最大 20MB,防止大文件耗尽磁盘
- **文件名处理**:存储文件名使用 UUID + 原扩展名,避免路径穿越攻击
- **类型记录**:记录 MIME 类型与原始文件名,但不限制文件类型(灵活支持各类文档)
- **权限校验**:下载与删除附件需登录认证,删除需为上传者本人或管理员

## 10. 技术选型说明

### 10.1 后端

| 技术 | 选型理由 |
| --- | --- |
| Express 4 | Node.js 生态最成熟的 Web 框架,中间件丰富,社区活跃 |
| better-sqlite3 | 同步 API、高性能、零配置。相比异步的 sqlite3 更简单可靠 |
| JWT (jsonwebtoken) | 无状态认证,适合 SPA 场景,无需服务端维护 Session |
| bcrypt | 业界标准的密码哈希方案,抗彩虹表攻击 |
| Zod | TypeScript 原生支持,运行时类型安全,与前后端类型共享无缝集成 |
| multer | Express 文件上传中间件,支持 multipart/form-data,配置灵活 |
| Nodemailer | Node.js 事实标准邮件库,支持 SMTP,HTML 模板,生态成熟 |

### 10.2 前端

| 技术 | 选型理由 |
| --- | --- |
| React 18 | 函数式组件 + Hooks,生态最成熟,招聘与维护成本低 |
| Vite 6 | 闪电般的冷启动、HMR,开发体验远超 Webpack |
| TailwindCSS 3 | 原子化 CSS,无需切换文件,设计一致性强 |
| Zustand 5 | 相比 Redux 更简洁,无需 Provider,TypeScript 支持优秀 |
| @dnd-kit/core | 现代化的拖拽库,支持触摸、键盘,API 设计优雅 |
| Recharts 2 | 基于 D3 构建,React API 友好,覆盖常见图表类型 |
| React Hook Form 7 | 相比 Formik 性能更好,使用 Controller 模式与受控组件集成 |
| lucide-react | 开源图标库,设计现代、一致,Tree-shake 友好 |

### 10.3 数据库

SQLite 适合本系统的原因:
- **规模匹配**:中小团队(≤100 人)使用,数据量在万级
- **运维简单**:单文件部署,无需 DBA
- **性能足够**:单用户场景下读写并发无压力
- **备份方便**:直接拷贝文件即可

未来如需要支持更大规模,可平滑迁移至 PostgreSQL/MySQL。
