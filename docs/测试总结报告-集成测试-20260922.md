## 四、发现并修复的缺陷

### 🔴 BUG-20260922-01：新装库工时登记失败（已修复，中等严重度）

- **现象**：全新初始化的数据库上，任务登记工时报错 `no column named billed_hours`，HTTP 500
- **根因**：[db.ts](file:///Volumes/DATA/Project/api/db.ts) 的 `task_hours` **建表语句缺 `billed_hours` 列**。存量生产库靠启动时的升级迁移（`ALTER TABLE ... ADD COLUMN`）补列，因此从未暴露；仅**全新部署**环境触发
- **修复**：建表语句补 `billed_hours DECIMAL(6,2) NOT NULL DEFAULT 0`，与迁移产物 schema 对齐
- **验证**：重建临时库 + 重放工时登记 → 201；随后的全量集成测试 D 区 3/3 通过
- **影响面**：仅影响新装部署；既有生产库不受影响

## 五、非缺陷偏差说明（测试脚本问题，共 5 项）

初测 6 个失败项经逐一定位，均非产品缺陷，为测试脚本用例问题，修正后复测通过：

1. 通知用例查错角色（owner 未被指派，应查被指派人）
2. 预算审批 403 用例误用 admin（admin 具备全权限，应改用项目负责人验证）
3. 越权台账用例选错记录（选中了成员本身可见的记录；且 member 未授权时先被权限矩阵 403 拦截，属既有合理口径）
4. **导入列名误写「作业日期」**——系统固定列名为「日期」，误写被归入扩展列导致查重键缺日期（反向验证了列头自动识别机制）
5. 「全部照导」用例漏传 `skipDuplicates: 'false'`（缺省即跳过重复，与产品确认过的语义一致）

排查过程中通过服务端诊断日志确认：导入查重键（项目+作业日期+问题）、预检/跳过式/照导三种模式的服务端行为**全部正确**。
